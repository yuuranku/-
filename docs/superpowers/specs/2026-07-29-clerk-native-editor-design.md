# PALIS 书记官原生精简编辑器设计规格

日期：2026-07-29

状态：用户已确认视觉方向，待复核书面规格

## 1. 目标

将书记官工作台从“外部 A4 设定卡 + 多段导航 + 大型横向窗口”收束为一套原生、竖向、低负担的档案编辑流程。

书记官只需要理解两件事：

1. 新增档案；
2. 修改已有档案。

在编辑器内完成填写并提交审核后，管理员负责审核、录入和发布；审核通过的内容才出现在公开档案系统。档案编号、提交版本和署名由系统生成，不由书记官手填。

## 2. 已确认的产品规则

### 2.1 档案类型与权限

- 九种现有档案类型均支持书记官新增：国家、组织、科考站、白幕入口、生态、人物、事件、异常、物种与标本。
- 九种类型均支持书记官对已有档案提出修改。
- 这替换当前“科考站和白幕入口仅能修改”的旧限制；权限检查、界面入口和工作流引擎必须一致更新。
- 书记官桌面不再暴露“暂存箱、审核回信、助手”等作为主操作入口；固定展示大尺寸的“新增档案”“修改档案”两个入口。
- 管理员保留审核队列，但将审核通过与正式录入合并为一个明确动作“通过并录入”。退回时提供退回说明。

### 2.2 书记官编辑器

- 工作台内不再加载九份 `public/templates/*.html` 的 iframe，也不再加载“自由修订补充页”作为表单。
- 旧设定卡文件可以继续作为历史/独立资料存在，但不再参与书记官工作流。
- 编辑器是原生 DOM 表单，使用统一的 PALIS 深蓝、米白、芥黄、砖红和青绿色调；Win95 只用于窗口边框、标题栏、控制按钮和任务栏。
- 编辑器右侧停靠，宽度为 `560–680px`，高度填满任务栏上方工作区；不会居中放大到遮住整张桌面。
- 编辑器仅有一个主滚动区和粘性底部操作栏；删除八项/十项横向分区导航。
- 桌面快捷图标的视觉图形增至约 `56–64px`，完整点击区至少 `96×96px`，标签清晰且不再显得细小。

### 2.3 九种独立新增表单

“新增档案”先打开九种档案类型选择，随后进入对应的一张原生精简表单；不能把九种类型压缩成一张仅靠“档案类型”下拉框切换的通用表单。九张表单共用窗口外观、正文区、补充内容区、系统状态和提交动作，但每张都有自己明确的核心字段与文案。

每张表单的字段都控制在“档案标题 + 2–3 个该类型真正需要的识别信息 + 档案正文 + 可重复补充内容”的范围内：

| 档案类型 | 独立表单的核心识别字段 |
| --- | --- |
| 国家 | 正式国名、档案时期、阵营/归档链 |
| 组织 | 正式名称、所属阵营/通道、成立或首次确认时间 |
| 科考站 | 站点名称、所属方、位置/坐标 |
| 白幕入口 | 入口名称、关联区域或站点、当前位置/风险 |
| 生态 | 名称、记录范围/地层、当前状态 |
| 人物 | 姓名或代称、所属组织/职务、活跃时期或当前状态 |
| 事件 | 事件名称、发生时间、地点 |
| 异常 | 异常名称、关联事件或地点、异常类型/严重度 |
| 物种与标本 | 名称、类别、发现地点或标本状态 |

每张表单之后都按相同顺序提供：

1. 档案正文（必填，单一主要叙述输入区）；
2. 可重复“补充内容”：每一项包含“自定义标题 + 内容”，可以新增或删除；
3. 可折叠的“补充索引信息”：只显示该类别仍未覆盖、但目录/专题视图可以使用的可选字段；管理员可在审核时补齐；
4. 提交审核。

创建时不出现正式档号、版本号、提交人、归档人等手工输入框。它们仅以只读系统状态显示。

### 2.4 修改表单

修改表单使用同一原生外观和字段结构，但它不是空白壳：选择目标档案后，系统必须从档案系统读取当前已发布的正式内容、已有补充项、已保存的索引信息、引用、媒体和版本信息，并将可编辑内容预填到表单。书记官在现有内容基础上改写或追加。

修改流程为：

1. 先选择九种档案类型，再从该类型的已有档案中选择目标档案（必填）；
2. 对存在多份正式正文的档案，选择要修改的具体记录；
3. 加载与目标档案类型相同的那张原生独立表单，并预填当前标题、该类型核心字段、正文、补充内容、已有可选索引信息、引用和媒体；同时以只读方式显示当前正式档号、当前版本、最后录入时间与最近署名；
4. 书记官修改内容或增加补充内容；
5. 提交审核。

读取失败时，表单必须显示可重试的错误状态，且不得退化为空白新建表单。修改提交引用不可变的基础版本，保证管理员能比对变更。发布后要同时更新档案正文和已变化的目录索引值，避免公开目录仍显示旧标题、旧坐标或旧状态。

## 3. 数据与流程

### 3.1 保持的数据合同

九张原生表单继续生成同一份 `EditorDocument v2` 数据合同，不建立第二套数据库结构；`templateCode` 决定具体的独立表单、字段标签和章节顺序：

```js
{
  schemaVersion: 2,
  templateCode: '01' /* 至 '09' */,
  category: 'station',
  abbreviation: 'LOG',
  title: '档案标题',
  values: { hero: '档案标题', body: '正文', customFieldId: '补充内容' },
  indexData: { title: '档案标题', optionalIndexKey: '可选值' },
  sections: [
    { id: 'main', label: '档案正文', fields: ['body'] },
    { id: 'custom', label: '补充记录', fields: ['customFieldId'] },
  ],
  fieldLabels: { body: '档案正文', customFieldId: '自定义标题' },
  references: [],
  media: [],
}
```

已有的正式渲染器会渲染 `values`、`sections` 和 `fieldLabels`，因此自定义补充项无需新建数据库表。目录投影继续使用 `indexData`；只有标题在书记官提交时强制要求，其余索引字段可以为空并在管理员审核界面补充。

### 3.2 状态与编号

```text
书记官新增或修改
  → 保存草稿（本地优先、云端同步）
  → 提交审核（生成投稿编号、投稿版本和提交署名）
  → 管理员“通过并录入”或“退回修改”
  → 通过：生成正式档号、写入版本历史、更新公开目录与正文
  → 档案系统显示正式记录
```

- 新增提交默认版本为 `v1`；修改提交按目标档案版本链递增。
- 投稿编号、版本号、提交者署名和提交时间在提交时由系统写入。
- 正式档号、正式版本、录入者与录入时间在“通过并录入”时由服务端写入。
- 失败不能清除本地草稿；审核通过但录入失败时，管理员能安全重试录入。

### 3.3 同步边界

- 配置 Supabase 的正常模式才是书记官跨账号提交、管理员审核和公开发布的正式路径。
- `LOCAL`/IndexedDB 模式仅保留作单机演示与开发验证，并明确标识为“本机演示”，不得被表述为跨账号同步成功。

## 4. 不做的事

- 不重写 Supabase 表、审核状态机或公开档案渲染器。
- 不要求书记官填写旧设定卡中的大量细节字段。
- 不新增第十种档案类型；“自定义”是每份档案内的补充内容，不是动态创建分类。
- 不继续显示 iframe、A4 纸张外观、模板内部操作栏或模板章节导航。
- 不改变外层公开档案馆的浏览体验。

## 5. 实现边界

主要改动预计集中在：

- `index.html`：书记官桌面只留下新增/修改入口；
- `src/style.css`：桌面图标尺寸与两入口布局；
- `src/archive-workflow/native-form-profiles.js`：九种原生精简表单的核心字段、字段标签、章节顺序和可选索引字段定义；
- `src/archive-workflow/workspace.js`：九种独立原生编辑器、动态补充字段、提交/审核显示和窗口停靠；
- `src/archive-workflow/workspace.css`：右侧竖向原生表单及管理员审核视图；
- `src/archive-workflow/category-profiles.js` 与 `index-fields.js`：将非标题索引字段改为可选并保留其目录投影；
- 发布路径：修改录入时同步更新档案级索引字段；
- 测试：增加原生编辑器、九类新增、可重复补充项、自动元数据、发布后目录同步、无 iframe、窄屏停靠和跨角色审核覆盖。

## 6. 验收标准

1. 书记官桌面一眼可见且仅以“新增档案”“修改档案”为主任务。
2. 点击后出现右侧竖向原生表单，无外部设定卡 iframe、无 A4 版式、无八项导航。
3. 新增时先选档案类型，再进入对应的独立原生表单；九张表单的字段标签和核心识别信息明显不同，但均保持精简并可重复添加任意自定义补充项。
4. 修改可定位既有档案和目标正文，打开对应类型的独立表单，并完整预填档案系统中的当前内容；新增内容与修改内容均可审核。
5. 提交自动写入投稿编号、版本和署名；审核通过自动写入正式档号和录入信息。
6. 管理员通过并录入后，正式档案正文及变更过的目录索引在档案系统中可见。
7. 现有草稿恢复、离线保护、审核退回和附件/引用数据不回归。
8. 单元测试、浏览器工作流验证和构建均通过；正式跨账号验收使用 Supabase 模式，单机演示单独标识。
