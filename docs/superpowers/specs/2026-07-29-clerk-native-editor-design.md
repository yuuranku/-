# PALIS 书记官原生精简编辑器设计规格

日期：2026-07-29

状态：用户已确认视觉方向，待复核书面规格

## 1. 目标

将书记官工作台从“外部 A4 设定卡 + 多段导航 + 大型横向窗口”收束为一套原生、竖向、低负担的档案编辑流程。

书记官只需要理解两件事：

1. 新增档案；
2. 修改已有档案。

本次不改变既有业务流程：书记官在编辑器内新建或修改后提交审核；管理员在管理员桌面批复“通过”或“打回修改”；通过的内容沿用原有正式录入与上线流程，最终才出现在公开档案系统。档案编号、提交版本和署名继续由系统生成，不由书记官手填。

## 2. 已确认的产品规则

### 2.1 档案类型与权限

- 九种现有档案类型均支持书记官新增：国家、组织、科考站、白幕入口、生态、人物、事件、异常、物种与标本。
- 九种类型均支持书记官对已有档案提出修改。
- 这替换当前“科考站和白幕入口仅能修改”的旧限制；权限检查、界面入口和工作流引擎必须一致更新。
- 书记官桌面不再暴露“暂存箱、审核回信、助手”等作为主操作入口；固定展示大尺寸的“新增档案”“修改档案”两个入口。
- 管理员保留现有审核队列与状态机，只将界面文案和信息呈现整理得更清楚：审核员可以“批复通过”或“打回修改”，打回时提供退回说明；批准后的正式录入与上线继续调用现有流程，不新增或跳过业务状态。

### 2.2 书记官编辑器

- 工作台内不再加载九份 `public/templates/*.html` 的 iframe，也不再加载“自由修订补充页”作为表单。
- 旧设定卡文件可以继续作为历史/独立资料存在，但不再参与书记官工作流。
- 编辑器是原生 DOM 表单，使用统一的 PALIS 深蓝、米白、芥黄、砖红和青绿色调；Win95 只用于窗口边框、标题栏、控制按钮和任务栏。
- 编辑器右侧停靠，宽度为 `560–680px`，高度填满任务栏上方工作区；不会居中放大到遮住整张桌面。
- 编辑器仅有一个主滚动区和粘性底部操作栏；删除八项/十项横向分区导航。
- 桌面快捷图标的视觉图形增至约 `56–64px`，完整点击区至少 `96×96px`，标签清晰且不再显得细小。

### 2.3 九种独立原生表单标准

“新增档案”先打开九种档案类型选择，随后进入对应的一张原生精简表单；不能把九种类型压缩成一张仅靠“档案类型”下拉框切换的通用表单。九张表单共用窗口外观、系统状态、关联档案选择、可重复补充内容和提交动作，但每张都从该类别原有设定卡与公开档案系统的实际字段中提取自己的标准。

每张表单固定分为三层：

1. **目录与识别**：保留该类别在公开目录、地图或专题视图真正需要的索引字段；
2. **核心档案内容**：将旧卡中最重要、语义相近的长字段合并为一到两个可读的叙述区，而不是逐格要求填写；
3. **更多资料**：可选字段、关联档案、媒体与可重复的“自定义标题 + 内容”。

新建时必须填写的标准如下。这里的“正文”不是通用空白框，而是按类型命名和引导的核心内容区：

| 档案类型 | 目录与识别（新建必填） | 核心档案内容（新建必填） | 可选但保留的既有信息 |
| --- | --- | --- | --- |
| 国家 | 正式国名、档案时期、阵营/归档链 | 国家概述：政治背景、极地能力与对白幕的参与方式 | 英文名/简称、主要参与机构、站点/入口、经济/军事等原有细项 |
| 组织 | 正式名称、阵营通道/归档链、成立或首次确认时期 | 机构定位与职责：性质、公开依托、公开/秘密职责与运行方式 | 工作简称、活跃期、前身、部门、人员来源、资源、管理站点/入口、审批与交接 |
| 科考站 | 站名、纬度、经度、所属方、站点类型、当前状态 | 站点概述与白幕关联：建站/公开职能、实际运行要点 | 英文名、行动网络、运行时期、关联入口、设施/保障、名册、事故、权限、证据与关联档案 |
| 白幕入口 | 入口名称、纬度、经度、所属方、入口类型、当前状态、危险级 | 通行与风险摘要：入口结构/下降或路线、通行条件、使用限制 | 地表开口、断面、下降深度、环境读数、探索地图、历史进入记录与关联档案 |
| 生态 | 名称、记录类型、首次记录时期、覆盖范围/所属地层、当前状态 | 标准剖面与生态描述；观测记录摘要 | 温湿度/气体/水/光/基质的细项、分布条件、采样方法、变化风险与关联档案 |
| 人物 | 姓名/代称、档案归属、主要组织、职务、活跃时期/最后状态、当前状态 | 项目职责与白幕关联；关键履历与专长摘要 | 外文名、出生/死亡/教育、照片、权限/接触材料、参与行动、离任/失踪与关联档案 |
| 事件 | 事件名称、发生时间、时间精度、地点；复核状态由系统预填为待审核，结束时间可选 | 事件概述；核心事实或证据摘要 | 来源卷、参与者、涉及站点/入口/机构、处置/后续影响、关联异常与未采信材料 |
| 异常 | 异常名称、母事件、发生时间、地点、异常类型、严重度；卷内状态由系统设为待审核 | 异常表现/实际观察；证据简述 | 正常基准、触发条件、受影响对象、处置、对母事件影响与关联档案 |
| 物种与标本 | 名称、类别、首次发现时间、发现地点、标本状态、危险级 | 特征与发现说明：形态/发现采集的核心事实 | 学术名/俗称、照片、生态/栖息地、保存材料、鉴定结论、关联生态/入口/事件与专业细项 |

创建时不出现正式档号、版本号、提交人、归档人等手工输入框。它们仅以只读系统状态显示。

旧设定卡的全部内容不会被丢弃。修改已有档案时，无法直接映射为上述核心字段的旧 `values` 和原章节，会以原字段标签组织进可折叠、可编辑的“原有补充资料”区域；提交时必须原样保留未修改的值。新建档案不强迫填写这些历史细项，但书记官可以通过“更多资料”或“添加补充内容”按需写入。

### 2.4 修改表单

修改表单使用同一原生外观和字段结构，但它不是空白壳：选择目标档案后，系统必须从档案系统读取当前已发布的正式内容、已有补充项、已保存的索引信息、引用、媒体和版本信息，并将可编辑内容预填到表单。书记官在现有内容基础上改写或追加。

修改流程为：

1. 先选择九种档案类型，再从该类型的已有档案中选择目标档案（必填）；
2. 对存在多份正式正文的档案，选择要修改的具体记录；
3. 加载与目标档案类型相同的那张原生独立表单，并预填当前标题、该类型目录字段、核心内容、补充内容、已有可选索引信息、引用、媒体和“原有补充资料”；已关联档案以可打开的摘要卡显示其现有标题、档号和内容摘要，避免书记官在修改时面对空壳；同时以只读方式显示当前正式档号、当前版本、最后录入时间与最近署名；
4. 书记官修改内容或增加补充内容；
5. 提交审核。

读取失败时，表单必须显示可重试的错误状态，且不得退化为空白新建表单。修改提交引用不可变的基础版本，保证管理员能比对变更。发布后要同时更新档案正文和已变化的目录索引值，避免公开目录仍显示旧标题、旧坐标或旧状态。

## 3. 数据与流程

### 3.1 保持的数据合同

九张原生表单继续生成同一份 `EditorDocument v2` 数据合同，不建立第二套数据库结构；`templateCode` 决定具体的独立表单、字段标签和章节顺序。每个原生表单配置都要把目录核心字段写入对应的 `indexData`，并将核心内容、历史字段和自定义条目写入 `values`/`sections`：

```js
{
  schemaVersion: 2,
  templateCode: '01' /* 至 '09' */,
  category: 'station',
  abbreviation: 'LOG',
  title: '档案标题',
  values: { hero: '档案标题', body: '正文', customFieldId: '补充内容' },
  indexData: { title: '档案标题', optionalIndexKey: '可选值' },
  sections: [
    { id: 'main', label: '档案正文', fields: ['body'] },
    { id: 'custom', label: '补充记录', fields: ['customFieldId'] },
  ],
  fieldLabels: { body: '档案正文', customFieldId: '自定义标题' },
  references: [],
  media: [],
}
```

已有的正式渲染器会渲染 `values`、`sections` 和 `fieldLabels`，因此自定义补充项无需新建数据库表。目录投影继续使用 `indexData`；每一类的“目录与识别”字段按上表保留为提交要求，避免地图、时间轴和专题目录失去所需信息。旧卡的非核心字段则可为空，但已有档案中的值必须被读取、显示和保存，管理员可以在审核界面补齐。

### 3.2 状态与编号

```text
书记官桌面：新建或修改档案
  → 保存草稿（本地优先、云端同步）
  → 提交审核（生成投稿编号、投稿版本和提交署名）
  → 管理员桌面：批复通过 或 打回修改
  → 打回：书记官读取原有内容与批复，继续修改后再次提交
  → 通过：沿用现有正式录入与上线步骤，生成正式档号、写入版本历史、更新公开目录与正文
  → 档案系统显示正式记录
```

- 新增提交默认版本为 `v1`；修改提交按目标档案版本链递增。
- 投稿编号、版本号、提交者署名和提交时间在提交时由系统写入。
- 正式档号、正式版本、录入者与录入时间在既有正式录入步骤中由服务端写入。
- 失败不能清除本地草稿；审核通过但录入失败时，管理员能安全重试录入。

### 3.3 同步边界

- 配置 Supabase 的正常模式才是书记官跨账号提交、管理员审核和公开发布的正式路径。
- `LOCAL`/IndexedDB 模式仅保留作单机演示与开发验证，并明确标识为“本机演示”，不得被表述为跨账号同步成功。

## 4. 不做的事

- 不重写 Supabase 表、审核状态机、批复/打回行为、正式录入步骤或公开档案渲染器。
- 不要求书记官把旧设定卡中的大量细节字段逐格填写，但不删除旧字段、旧正文或其公开渲染语义。
- 不新增第十种档案类型；“自定义”是每份档案内的补充内容，不是动态创建分类。
- 不继续显示 iframe、A4 纸张外观、模板内部操作栏或模板章节导航。
- 不改变外层公开档案馆的浏览体验。

## 5. 实现边界

主要改动预计集中在：

- `index.html`：书记官桌面只留下新增/修改入口；
- `src/style.css`：桌面图标尺寸与两入口布局；
- `src/archive-workflow/native-form-profiles.js`：九种原生精简表单的目录字段、核心叙述字段、旧字段映射/保留规则、字段标签和章节顺序；
- `src/archive-workflow/workspace.js`：九种独立原生编辑器、动态补充字段、提交/审核状态展示和窗口停靠；既有“提交 → 审核通过/打回 → 正式录入/上线”调用顺序保持不变；
- `src/archive-workflow/workspace.css`：右侧竖向原生表单及管理员审核视图；
- `src/archive-workflow/category-profiles.js` 与 `index-fields.js`：将九类目录字段的校验规则对齐到本规格的“目录与识别”标准，并保留其目录投影；
- 发布路径：修改录入时同步更新档案级索引字段；
- 测试：增加九类表单标准、旧档案字段预填且不丢失、可重复补充项、自动元数据、发布后目录同步、无 iframe、窄屏停靠和跨角色审核覆盖。

## 6. 验收标准

1. 书记官桌面一眼可见且仅以“新增档案”“修改档案”为主任务。
2. 点击后出现右侧竖向原生表单，无外部设定卡 iframe、无 A4 版式、无八项导航。
3. 新增时先选档案类型，再进入对应的独立原生表单；九张表单均保留其公开档案系统需要的目录字段和从旧卡压缩而来的核心内容，且可重复添加任意自定义补充项。
4. 修改可定位既有档案和目标正文，打开对应类型的独立表单，并完整预填档案系统中的当前内容；旧字段会保留在“原有补充资料”中，任何未修改数据不得丢失；新增内容与修改内容均可审核。
5. 提交自动写入投稿编号、版本和署名；管理员可批复通过或打回修改；既有正式录入步骤自动写入正式档号和录入信息。
6. 批复通过并完成原有上线流程后，正式档案正文及变更过的目录索引在档案系统中可见；打回后书记官能读取原内容和批复继续修改。
7. 现有草稿恢复、离线保护、审核退回和附件/引用数据不回归。
8. 单元测试、浏览器工作流验证和构建均通过；正式跨账号验收使用 Supabase 模式，单机演示单独标识。
