## 1. 结论

### 1.1 总结论

**有条件可行。**

现有 Supabase、Vite 和九类公开档案界面可以继续使用，不必推倒重做；但不能继续采用“审核后向通用 `archives` 表写几个字段，再把云端记录临时拼进静态 `ARCHIVE_ROOTS`”的接法。

可行方案必须增加一个正式的“档案索引投影层”：

```text
书记官草稿
  → 审核版本
  → 正式档案版本（完整内容）
  → 九类索引投影（列表、时间、坐标、阵营、地层等）
  → 公开档案系统
```

其中：

- 完整内容解决“这份档案写了什么”。
- 索引投影解决“它在九类目录里出现在哪里、按什么排序、怎样被搜索”。
- 发布时间只表示管理动作发生的时间，不能代替事件发生时间、建站时间或发现时间。
- 用户自由增加的词条只保存在当前档案版本中，不修改全局模板，也不污染其他档案。
- 九类排版、PALIS 配色字体、纸张与窗口质感、弹窗、任务栏、拖拽、焦点、最小化、还原和关闭动效均作为产品合同冻结；底层重写不得造成换肤。
- 实施前先交付无需登录、无需连接 Supabase 的本地管理员验证模式，使九类完整流程可在本机反复验证。

### 1.2 不能接受的伪修复

以下做法即使短期“看起来能显示”，也应判定不可行：

1. 只给事件页面增加第 27 个固定坐标。
2. 继续用 `published_at` 作为事件发生年份。
3. 继续把云端记录与静态数组按档号临时拼接，且没有唯一权威来源。
4. 只在 `archives` 表不断增加九类专用列。
5. 让自由词条直接修改九类全局模板。
6. 只在书记官前端隐藏“新建”按钮，却不在数据库拒绝书记官新建科考站、白幕入口的请求。
7. 审核、录入、生成索引分成多次无事务写入，允许出现“正文已发布但索引没有”的半完成状态。
8. 验收只看自动化测试通过，不在真实角色、真实数据库和九类公开索引中走完整流程。
9. 借重写之名换成 React、Tailwind、通用组件库或普通后台风格。
10. 同一个阶段同时重写数据库发布、九类布局和窗口管理，导致无法判断回归来源。
11. 只在登录线上账号后才能验证，或让本地测试数据写入正式 Supabase。

## 2. 已核实的现状

### 2.1 九类编辑器复杂度

现有九份设定卡合计约 **477 个独立输入项**，单类约 **25–66 个字段**、**5–12 个章节**。技术上可以序列化和保存，但不适合作为所有书记官每次都必须完整填写的统一表单。

问题不是字段“太多”本身，而是三层概念混在了一起：

- 档案登记所必需的核心字段。
- 某一档案类别用于公开索引的字段。
- 仅当前记录需要的叙述性词条。

### 2.2 已复现的事件索引故障

当前线上数据中，书记官提交、管理员审核及发布动作已经成功产生公开事件记录；但公开事件时间索引无法可靠显示它。

根因链如下：

1. 正式档案表只保存通用字段，没有保存事件发生日期等索引字段。
2. 云端记录转换时把 `published_at` 当成事件年份。
3. 公共目录读取不到版本正文里的真实事件日期。
4. 事件胶片布局只有 26 个固定槽位。
5. 第 27 条事件会与第 1 条记录复用坐标并发生重叠。

因此，该故障不是单一 CSS 或排版问题，而是“审核工作流没有向旧档案索引提供正式数据合同”的架构问题。

### 2.3 九类公开索引的扩展现状

| 类别 | 当前索引特点 | 当前扩展风险 | 改造判断 |
|---|---|---:|---|
| 国家 | 条目循环基本动态，界面仍写死数量 | 中 | 保留视觉，改动态计数与正式投影 |
| 组织 | 三条阵营通道固定，通道内条目动态 | 中 | 阵营为受控值，条目动态 |
| 科考站 | 已知站点有固定位置，未知站点有经纬度回退 | 中 | 业务上禁止玩家新建，只允许修改既有站点 |
| 白幕入口 | 条目循环动态，界面写死总数 | 中 | 业务上禁止玩家新建，只允许修改既有入口 |
| 生态 | 七层地层、读数和几何关系高度固定 | 高 | 书记官可新增生态档案；现有七层改为可容纳多条档案的分组，管理员可设定分组 |
| 人物 | 卡片与关系网可从数据动态生成 | 低 | 可开放新建与修改 |
| 事件 | 26 个固定胶片位置 | 极高 | 必须改为动态时间轨道或虚拟化布局 |
| 异常 | 条目循环动态，界面写死总数 | 中 | 改动态计数、排序和分类投影 |
| 物种 | 植物/动物分组和高度计算基本动态 | 低 | 可开放新建与修改 |

## 3. 外部依据与可复现逻辑

本方案不照抄某一套产品界面，而是组合档案行业与成熟开源系统中已经验证的逻辑。

### 3.1 档案学依据

- ICA《Records in Contexts》强调记录、实体、属性和关系，并允许扩展描述；适合“固定核心 + 当前档案自定义词条 + 结构化关系”。
- ISO 15489 要求记录、元数据、职责、控制措施和长期管理过程共同存在。
- Library of Congress EAD3 将日期、地名、关系、维护状态和控制信息分开表达，支持单一日期、范围和集合日期。
- NARA 的接收逻辑区分草稿、提交、审批、移交/接收及检索工具，说明“批准内容”和“可在索引中发现”不能视为同一件事。

### 3.2 开源系统依据

- ArchivesSpace 将后台 API、工作人员界面、公开界面和 Solr 索引器分离；其资源记录采用固定必需字段加可重复日期、说明、分类、关系和用户自定义字段。
- AtoM 默认新描述为草稿；贡献者可以创建和修改草稿但不能发布；已发布内容被无发布权用户修改后重新进入草稿。
- CollectiveAccess 将编目后台与公开展示分离，并支持字段级、类型级、来源级和条目级权限。
- DSpace 区分工作区条目、工作流条目、工作流步骤和正式归档版本。

### 3.3 当前技术栈依据

- Supabase 的数据库本质为 PostgreSQL，可通过 RLS 将权限落实到每一行，而不是只依赖界面隐藏。
- PostgreSQL 函数可以把多张表的发布动作放在同一事务中；抛出异常时整次写入回滚。
- `jsonb` 适合保存当前档案独有的自定义词条；常用检索字段应投影为明确的索引键，而不是每次扫描整份 JSON。

## 4. 推荐的目标结构

### 4.1 四层档案模型

```text
身份层 archives
  └─ 档号、类别、标题、当前正式版本、记录状态

版本层 archive_versions
  └─ 每次正式录入的不可变完整内容

工作流层 drafts / contributions / reviews
  └─ 谁编辑、谁提交、谁审核、批复与修改轮次

检索层 archive_index_entries
  └─ 九类公开目录真正消费的日期、坐标、阵营、分组、排序键
```

### 4.2 需要新增或调整的数据职责

| 对象 | 职责 | 是否公开读取 |
|---|---|---|
| `archive_category_profiles` | 九类规则、是否可新建、必填索引键、投影版本 | 是，受控只读 |
| `archive_number_counters` | 九类正式编号计数器；发布时原子取号 | 否 |
| `system_releases` | 当前系统版本及版本主题，例如 `VER 0.1 / 白幕初垂` | 是，只读 |
| `archives` | 正式档案身份与当前版本指针 | 公开记录可读 |
| `archive_versions` | 不可变的正式内容快照 | 按可见性读取 |
| `archive_contributions` | 草稿和提交上下文 | 仅相关书记官/审核者 |
| `archive_reviews` | 审核意见和决定 | 仅相关人员 |
| `archive_index_entries` | 公开九类索引的标准数据 | 公开记录可读 |
| `archive_signature_snapshots` | 提交时的书记官署名、审核署名和版本章快照 | 按档案可见性读取 |
| `archive_audit_log` | 关键操作证据 | 管理员/审计员 |
| `archive_references` | 正向、反向档案关系 | 按目标可见性读取 |

### 4.3 自由词条的数据结构

自定义词条不是数据库新列，也不是全局模板字段。每个词条属于当前版本：

```text
词条 ID：系统生成且永久稳定
显示名称：书记官填写，例如“宗教”
类型：短文本 / 长文本 / 数字 / 日期 / 日期范围 / 选项 / 是非 / 档案引用
值：当前档案的值
所属章节：现有章节或当前档案自建章节
排序：仅控制当前档案中的位置
公开性：跟随该版本和档案可见性
来源说明：可选
```

规则：

1. 书记官可重命名或删除自己在当前草稿中增加的词条。
2. 九类固定核心字段不能被书记官删除或改名。
3. 自定义词条不会自动出现在同类其他档案中。
4. “宗教”改名为“信仰”时，内部词条 ID 不变，版本差异可以正确追踪。
5. 只有管理员以后主动执行“提升为类别模板字段”，才可能影响后续新档案；该能力不属于本期必需范围。

### 4.4 索引投影示例

| 类别 | 必须投影的索引键示例 |
|---|---|
| 国家 | 名称、阵营/状态、排序名、显示代码 |
| 组织 | 名称、阵营通道、成立/活跃时间、显示代码 |
| 科考站 | 站名、经纬度、状态、所属方、显示代码 |
| 白幕入口 | 入口名、经纬度、状态、危险级、显示代码 |
| 生态 | 地层 ID、深度范围、状态、排序序号 |
| 人物 | 姓名、阵营/组织、活跃年代、关系节点标签 |
| 事件 | 事件开始时间、结束时间、时间精度、地点、排序时间 |
| 异常 | 首次记录时间、等级、类型、状态、排序时间 |
| 物种 | 名称、植物/动物/其他分类、发现时间、危险级 |

这些键由正式版本内容计算得出，管理员在录入前看到“索引预览”，不能手工另抄一份互相矛盾的数据。

## 5. 权限模型

### 5.1 对外角色保持简单，内部按能力校验

第一期可以继续保留当前三个角色，避免立刻扩大账号系统：

| 角色 | 用户可理解的身份 | 能力 |
|---|---|---|
| `observer` | 观察员 | 阅读公开或被授权档案 |
| `clerk` | 书记官 | 建草稿、改自己的草稿、提交、撤回、申请修改 |
| `admin` | 管理员兼审核员 | 审核、录入、发布、封存、离线、账号与类别规则管理 |

数据库内部不只检查角色名称，还检查具体能力和记录关系，例如：

- 是否为草稿所有者。
- 是否为当前审核人。
- 类别是否允许新建。
- 目标档案是否允许修订。
- 基础版本是否仍为当前版本。
- 当前状态是否允许该操作。

如果以后需要把“审核员”和“系统管理员”拆开，只增加角色到能力的映射，不重写整个工作流。

### 5.2 九类新建策略

委托人已于 2026-07-28 确认最终业务规则：

| 类别 | 书记官新建 | 书记官申请修改 | 管理员新建 | 管理员修改/设定 |
|---|---:|---:|---:|---:|
| 国家 | 允许 | 允许 | 允许 | 允许 |
| 组织 | 允许 | 允许 | 允许 | 允许 |
| 科考站 | **禁止** | 允许 | 允许 | 允许 |
| 白幕入口 | **禁止** | 允许 | 允许 | 允许 |
| 生态 | 允许 | 允许 | 允许 | 允许 |
| 人物 | 允许 | 允许 | 允许 | 允许 |
| 事件 | 允许 | 允许 | 允许 | 允许 |
| 异常 | 允许 | 允许 | 允许 | 允许 |
| 物种 | 允许 | 允许 | 允许 | 允许 |

管理员的“设定”包括：

- 新建九类中的任何正式档案，包括新科考站和新白幕入口。
- 修改九类类别的受控选项、索引映射和必要字段。
- 设置档案可见性、运行状态和正式索引呈现。
- 预览设定变更会影响哪些档案。

类别设定本身也必须版本化并写审计日志。管理员调整模板或受控选项时，不得静默改写已有正式版本；如需批量迁移，必须先生成影响预览，再作为独立迁移任务执行。

## 6. 状态机

旧方案把“审核进度”“是否公开”“封存/离线”混成一列，容易产生非法跳转。新方案拆成三条互不混淆的状态。

### 6.1 工作流状态

```text
draft
  → submitted
  → in_review
  → changes_requested → draft
  → approved_for_accession
  → rejected

submitted → withdrawn → draft
```

### 6.2 正式版本状态

```text
unpublished → published → superseded
```

### 6.3 档案运行状态与可见性

```text
record_status: active / sealed / offline / retired
visibility: public / restricted / private
```

封存和离线不是“审核结果”，不能覆盖审核历史。

## 8. 九类索引改造方案

### 8.1 共同要求

每一类都必须完成：

1. 从 `archive_index_entries` 读取，而不是从审核表或发布时间猜测。
2. 数量文字从真实记录数生成。
3. 排序使用类别明确的排序键。
4. 新记录数量增加时不重叠、不越界、不覆盖旧记录。
5. 点击索引项必须打开生成该索引的同一正式版本。
6. 索引生成失败时，正式发布整体回滚。
7. 保留旧静态档案作为迁移期间的只读回退，不作为长期第二真源。

### 8.2 事件索引专项

建议将 26 个固定坐标替换为基于时间的动态轨道：

- 精确日期按时间比例放置。
- 只有年份的记录使用年中占位并标识精度。
- 日期范围显示为区间。
- 同一时间附近的多条记录使用自动分层或聚类，不能重叠。
- 数量较多时使用可拖动/虚拟化轨道，不一次创建无限 DOM。
- 发布时间仅在详情的管理信息区显示，不参与时间排序。

### 8.3 固定目录专项

科考站和白幕入口：

- 公开索引可以更新已有条目的内容、坐标、状态和显示名称。
- 书记官界面没有“空白新建”路径。
- 书记官直接构造 API 请求新建时也会被数据库函数拒绝。
- 管理员拥有单独的新增和设定能力，不与书记官修改权限共用。

## 9. 迁移路线与停机策略

### 阶段 0：冻结基线

1. 导出当前正式档案表、版本表和九类静态目录的清单。
2. 记录九类条目数、档号、标题、排序、坐标/日期等。
3. 保存事件故障样本及截图。
4. 建立回滚版本，不改变生产数据。

**通过条件：** 可以证明改造前系统有哪些记录，且能恢复。

### 阶段 1：建立统一索引合同

1. 定义九类 `index_data` 结构和版本号。
2. 为九类编写投影器与验证器。
3. 给现有静态档案生成同结构的投影测试夹具。
4. 不改公开界面，只验证数据一致性。

**通过条件：** 九类现有档案都能生成合法投影，数量和关键字段一致。

### 阶段 2：改造工作流与权限

1. 增加类别策略、索引表和审计表。
2. 落实 RLS 和数据库发布函数。
3. 编辑器支持当前档案自定义词条。
4. 固定类别在前端和数据库双重禁止书记官新建。

**通过条件：** 直接绕过界面的越权请求也失败。

### 阶段 3：逐类接入公开索引

建议顺序：

1. 人物、物种（当前最接近动态）。
2. 国家、组织、异常（主要修正计数和分类投影）。
3. 科考站、白幕入口（固定策略与坐标验证）。
4. 生态（需先确认固定地层策略）。
5. 事件（单独完成动态时间轨道和压力测试）。

每类独立开关；一类失败时只回退该类到旧索引。

### 阶段 4：迁移权威来源

1. 将现有静态档案导入正式档案/索引结构，或生成一份可重复导入的权威清单。
2. 比较新旧条目总数、档号、标题、打开结果和排序。
3. 新系统通过后，将数据库索引设为唯一真源。
4. 删除长期的“静态 + 云端按档号拼接”逻辑。

**通过条件：** 九类逐项对账为零差异；新增记录无需改源代码即可出现。

## 10. 免费服务器容量与优化可行性

### 10.1 当前部署结论

当前架构为：

```text
Cloudflare Workers Static Assets
  └─ 公开页面、Three.js、图片、字体、九类视觉

Supabase Free
  ├─ PostgreSQL / RLS / Auth
  ├─ 书记官草稿、审核、版本、索引
  ├─ 私有附件
  └─ 少量账号管理 Edge Functions
```

**结论：按当前项目规模和预期的低频书记官工作流，免费层可以承载。**

主要压力不在 Cloudflare 静态页面，而在：

1. Supabase 的 500MB 数据库容量。
2. Supabase 的 1GB 文件存储。
3. 每月 5GB 数据库出口和 5GB 缓存出口。
4. 免费项目低活跃 7 天后可能暂停。
5. 免费项目没有日常自动备份。
6. 当前页面首轮加载约 21MB，虽然不会压垮 Cloudflare，但会拖慢玩家设备和移动网络。

| 首轮请求目标 | 45 个以内 |
| 首轮压缩 JavaScript | 450KB 以内 |

“5,000 个版本”是保守运营目标，不是 PostgreSQL 的技术极限。正式上线后以真实 `pg_database_size`、表大小和索引大小为准，不能只按记录数猜测。

### 10.5 数据库优化方案

1. **公开索引与完整正文分开。** 首页和九类目录只读投影字段；打开详情时才取当前正式版本。
2. **全部列表使用游标分页。** 不再使用“最多 100 条然后假装是全部”的模式。
3. **常用条件建立组合/部分索引。** 重点为：
   - `category + visibility + sort_key`
   - `owner_id + workflow_status + updated_at`
   - `reviewer_id + workflow_status + submitted_at`
   - `archive_id + version_no`
   - 未读通知的 `recipient_id + read_at`
4. **不对所有 JSONB 字段建立万能 GIN。** 只为确实需要搜索的自定义词条建立有证据的索引，避免写入变慢和磁盘膨胀。
5. **草稿原地更新。** 自动保存只更新当前草稿行，不为每次按键创建历史版本。
6. **正式版本只在提交/录入节点生成。** 审核快照和正式版本不可变。
7. **通知和审核证据分离。** 审核记录长期保留；已读通知可按保留策略归档，避免重复存一份长批复。
8. **每次迁移后运行 Supabase Security/Performance Advisor。** 检查缺失索引、重复索引、RLS 和表膨胀。

### 10.6 自动保存降载

当前本地保存 800ms、云端保存 5 秒。建议改为：

- 本地仍在 800ms 内保存，保证断电恢复。
- 云端在停止输入 15 秒后保存。
- 点击提交、关闭编辑器或切换档案时强制保存。
- 内容无语义变化时不发请求。
- 同一编辑器最多平均 4 次云端写入/分钟。
- 失败重试采用 15/30/60 秒退避，不形成请求风暴。
- 连续输入时不保存每一个字符版本。

即使 10 位书记官同时编辑，目标上限也约为 40 次写入/分钟，符合此类低频管理系统的免费实例定位。

### 10.7 公开读取和出口优化

公开玩家不应每次刷新都直接从 Supabase 拉取九类完整目录。

推荐增加一个很薄的 Cloudflare 索引缓存接口：

```text
玩家
  → Cloudflare /api/archive-index/{category}
  → 命中 1 小时边缘缓存：直接返回
  → 未命中：向 Supabase 读取紧凑投影后缓存
```

规则：

- 静态图片、字体和脚本仍由 Cloudflare 静态资源直接提供。
- 动态 Worker 只处理紧凑索引，不渲染整站。
- 每类缓存 1 小时；管理员正式发布后只清除对应类别缓存，使新档案立即可见。
- 缓存失效或 Supabase 暂停时，返回最后一次成功索引，并标记“索引可能延迟”。
- 档案详情按点击加载，并缓存公开版本；封存/离线后立即失效。

按每类 60KB、九类持续每小时各回源一次的理论高位估算，数据库索引出口约 390MB/月，远低于 5GB；实际访问通常更低。

### 10.8 附件优化

Supabase Storage 的 1GB 是免费方案最容易先触顶的资源。建议：

| 项目 | 规则 |
|---|---|
| 图片 | 浏览器上传前压缩为 WebP，最长边不超过 1600px，目标不超过 1MB |
| PDF/文档 | 单文件最多 5MB |
| 单份草稿 | 最多 5 个附件，总量最多 10MB |
| 重复文件 | 保存 SHA-256，至少在同一档案内去重 |
| 公开展示图 | 不从数据库正文内嵌 Base64 |
| 放弃/拒绝草稿附件 | 保留期限需由委托人确认；审核记录和文件元数据不随附件清理 |

存储达到 600MB 时停止继续扩大附件额度，并启动迁移；达到 800MB 时禁止普通用户新增附件，只允许管理员清理或迁移。

如果附件量持续增长，推荐迁移到 Cloudflare R2：

- 免费 10GB 存储。
- 每月 100 万次写类操作、1000 万次读类操作。
- 互联网出口免费。
- Supabase 继续保存附件元数据、权限和审计。
- 私有文件通过 Cloudflare Worker 校验 Supabase 登录令牌后读取。

R2 不必在第一阶段立即引入，但必须在 Supabase Storage 达到 600MB 前完成选择与演练。

### 10.9 前端减重

1. 书记官人物照片和笔记图只在打开对应窗口时加载，预计首轮可直接减少约 10MB。
2. 吉祥物多帧改成按需帧、压缩 WebP 或精灵图。
3. 地球、舱体和大图提供 WebP/AVIF 与合适尺寸，不给小屏下载桌面大图。
4. 将公开首页、九类索引、档案详情、登录工作台拆成独立代码块。
5. Supabase、编辑器和九类 HTML 模板只在登录并打开工作台后加载。
6. 九类完整正文不放在首屏 JavaScript 中；索引只带标题和定位字段，正文点击后再载入。
7. 图片默认 `loading=lazy`，只有首屏必需图使用预加载。

### 10.10 免费项目暂停与降级

Supabase 官方说明，免费项目在 7 天低活动后可能暂停，且通常少量日常用户请求足以保持活跃，但不能把“不会暂停”当作保证。

降级行为：

- 公开站继续由 Cloudflare 返回最后成功的只读档案索引和静态内容。
- 工作台显示“档案数据库暂不可用”，不把权限错误伪装成断网。
- 书记官仍可保留浏览器本地草稿，但恢复前不能宣称已同步或已提交。
- 管理员收到恢复说明；项目恢复后书记官手动核对并同步。
- 不通过高频无意义请求规避暂停。

### 10.11 免费备份方案

Supabase 免费层没有自动日备份，因此“能运行”不等于“足够可靠地保存档案”。

最低备份制度：

1. 每次生产数据库迁移前执行逻辑导出。
2. 每周导出数据库结构和数据。
3. 同步导出私有附件清单及文件。
4. 备份加密后保存到 Supabase 之外的两个位置。
5. 保留最近 7 个周备份和 12 个每月备份。
6. 每季度在临时环境做一次恢复演练。
7. 在实施报告中记录备份文件校验和与恢复结果，但不记录密钥。

如果不能执行这套备份制度，本项目可以作为游戏网站运行，但不应被称为可靠的长期档案管理系统。

### 10.12 容量红线

| 指标 | 预警 | 必须处理 | 硬停止/降级 |
|---|---:|---:|---:|
| 数据库占用 | 250MB | 300MB | 400MB |
| Supabase Storage | 500MB | 600MB | 800MB |
| 数据库出口/月 | 2.5GB | 3.5GB | 4.2GB |
| Edge Functions/月 | 250,000 | 350,000 | 450,000 |
| 动态 Worker/日 | 50,000 | 75,000 | 90,000 |
| 首轮页面传输 | 10MB | 12MB | 超过 15MB 不验收 |

达到“必须处理”线时，不能继续无条件开放新附件或扩大查询；必须先优化、迁移或升级。硬停止线保留约 10%–20% 缓冲，防止免费额度突然触顶导致整个工作台不可用。

## 11. 风险、成本与否决条件

| 风险 | 等级 | 控制措施 |
|---|---:|---|
| 静态目录与数据库双真源 | 极高 | 分阶段导入并最终只保留一个权威来源 |
| 九类索引语义不同 | 高 | 共享合同 + 九个小型投影器，不做一个万能大函数 |
| 自由词条破坏模板 | 高 | 自定义词条仅属于当前版本，固定核心字段受保护 |
| 发布正文成功、索引失败 | 极高 | 单一事务，任何一步失败整体回滚 |
| 固定类别被绕过前端新建 | 高 | 类别策略同时在 UI、函数和 RLS/约束校验 |
| 旧版本被并发覆盖 | 高 | `base_version_id` 乐观并发检查 |
| 事件大量增加后再次重叠 | 高 | 动态布局、聚类/分层、27/100/500 条压力测试 |
| 免费额度与性能 | 中 | 列表分页、投影表常用列索引、JSONB 只存扩展内容 |
| 管理员权限过大 | 中 | 能力校验、审计日志；后续可拆审核员角色 |
| 迁移导致公开站中断 | 中 | 类别级开关、旧索引只读回退、生产迁移前快照 |
| Supabase 免费项目暂停 | 中 | Cloudflare 最后成功索引回退、本地草稿和明确恢复提示 |
| 免费层无自动备份 | 极高 | 周逻辑备份、双位置保存、季度恢复演练 |
| Supabase Storage 先触顶 | 高 | 10MB/草稿预算、600MB 迁移红线、R2 预案 |
| 首屏 21MB 影响玩家设备 | 高 | 懒加载、图片压缩、代码拆分，验收目标 8MB |

以下任一条件不满足，应暂停实施：

1. 不允许新增数据库迁移或发布函数。
2. 不愿确定九类“谁能新建”的规则。
3. 要求静态目录和数据库永久同时作为权威来源。
4. 不允许做生产前数据快照和回滚。
5. 不接受事件索引从固定 26 槽改为动态布局。
6. 不允许使用真实角色和真实 Supabase 环境做验收。
7. 不允许设置免费额度红线、附件总预算或数据库备份。

## 13. 实施前需委托人确认的决策

### 已确认：九类新建权限

七类允许书记官新建和申请修改；科考站、白幕入口仅允许书记官申请修改；管理员九类均可新建、修改和设定。实施不得再次把这一项作为待定内容。

### 决策 A：审核角色

建议第一期不新增独立审核员账号类型，由管理员兼任审核；数据库内部仍按能力设计，为以后拆分预留。

### 决策 B：录入动作

建议保留“两步”：

1. 审核员批准进入录入。
2. 管理员核对档号、可见性和索引预览后，点击“正式录入并发布”。

这样能防止内容判断和档案登记混为一次不可复核的点击。

### 决策 C：附件保留

需要确认放弃、撤回和拒绝草稿中的附件保留期限。推荐：

- 正式版本附件长期保留。
- 审核意见和附件元数据长期保留。
- 未进入正式版本的附件保留 90 天后进入管理员清理清单，不自动直接删除。

## 15. 九类档案填写合同

所有九类共同遵守：

1. 档号、提交编号、登记日期、署名、审核人、版本号和索引序号由系统生成。

## 16. 空白扩展页与空白修改页

### 16.1 页面外观

扩展页和修改页打开时，正文区域就是一张空白纸，不复制原档案的九类大表。

空白正文之外固定显示：

```text
目标档案：系统带入
提交类型：扩展页 / 修改申请
书记官：登录账号自动署名
基础档案版本：系统带入
提交轮次：系统生成
PALIS VER 0.1 / 白幕初垂
创建时间 / 提交时间：系统生成
```

书记官不能编辑以上行政数据。

### 16.2 空白页可以写什么

- 普通标题和正文。
- 自建章节。
- 自建“词条名称 + 词条内容”。
- 表格。
- 时间线。
- 档案引用。
- 图片和附件。
- 多张空白页。

保存格式是结构化内容块，不保存任意可执行 HTML。

### 16.3 审核后的两种去向

**作为补充页收录：**

- 原文、顺序和署名完整保留。
- 显示在目标档案的“补充记录”中。
- 不自动覆盖主档案核心字段。
- 不改变九类索引，除非管理员另行发起主档案修订。

**合并为主档案新版本：**

- 管理员在审核台把自由内容映射到现有核心字段、新增词条或索引字段。
- 系统显示旧值、新值、索引变化和正式排版预览。
- 管理员确认后生成主档案新版本。
- 不使用 AI 或模糊规则自动猜测应修改的字段。

## 17. 自动编号、署名与版本

### 17.1 书记官无需填写的内容

- 档号。
- 事件编号、人物编号、物种编号等类别编号。
- 提交编号。
- 登记日期、提交时间、审核时间、发布时间。
- 书记官姓名。
- 审核管理员姓名。
- 系统版本和版本主题。
- 草稿修订轮次、正式档案修订号。
- 索引顺序和布局位置。

现有九类设定卡中的 `档号`、`登记日期`、`经办书记官` 改为只读系统栏。

### 17.2 自动编号方案

为了保留现有公开档案习惯，使用当前类别前缀：

| 类别 | 自动档号 | 当前数据后的下一号示例 |
|---|---|---|
| 国家 | `N` + 顺序号 | `N19` |
| 组织 | `O` + 顺序号 | `O25` |
| 科考站 | `ST` + 顺序号 | `ST21` |
| 白幕入口 | `EN` + 顺序号 | `EN19` |
| 生态 | `E` + 顺序号 | `E08` |
| 人物 | `P` + 顺序号 | `P47` |
| 事件 | `EV` + 顺序号 | `EV27` |
| 异常 | `A` + 顺序号 | `A26` |
| 物种 | `S` + 顺序号 | `S23` |

既有 `US-MCM`、`US-K1`、`HZ-6` 等不重新编号，作为正式别名或行动代号保留。新科考站和入口可以由管理员设置呼号别名，但正式档号仍由系统生成。

取号规则：

1. 草稿和审核阶段显示“待分配”，不占正式档号。
2. 管理员点击“正式录入并发布”时才取号。
3. 数据库按类别锁定计数器并加一。
4. 两位管理员同时发布也不能取得同一编号。
5. 已使用编号永不回收、永不重新分配。
6. 修改既有档案沿用原档号，只增加档案修订号。

### 17.3 三种版本必须分开

| 名称 | 示例 | 用途 |
|---|---|---|
| 系统发行版本 | `VER 0.1 / 白幕初垂` | 记录内容是在世界观哪个发行版本中提交 |
| 提交轮次 | `REV 01`、`REV 02` | 书记官被退回后第几次提交 |
| 档案修订号 | `R01`、`R02` | 正式档案已经发布了几个版本 |

### 17.4 每次提交的署名章

提交时系统从登录账号生成快照：

```text
书记官：XXX
提交编号：SUB-20260728-0001
提交轮次：REV 01
基础档案版本：R02（新建档案则为“新建”）
PALIS VER 0.1 / 白幕初垂
提交时间：2026-07-28 21:30
```

署名不是可编辑文本。账号以后改名或停用，历史提交仍保留当时的署名快照，同时保存不可见的用户 ID 供审计。

### 17.5 正式档案登记章

```text
EV27 · R01
收录书记官：XXX
审核管理员：XXX
PALIS VER 0.1 / 白幕初垂
正式录入：2026-07-28 22:10
```

修改后的版本同时显示原始收录者和本次修改者，不用新署名覆盖旧署名。

九类现有排版属于必须保留的产品外观；数据库、DOM、JavaScript、组件和布局算法允许全部重写。

| 类别 | 必须保留 | 动态扩展实现 |

| 白幕入口 | 坐标节点网 | 动态节点、聚合、避让和缩放 |
| 生态 | 纵向地层 | 每层容纳多份档案；管理员可设定分组 |
| 人物 | 档案袋和关系网 | 动态节点、关系线、分页/聚类 |

| 异常 | 时间诊断台/轮盘 | 动态数量、等级和时间排序 |

## 19. 美术、弹窗与动效零改版合同

### 19.1 冻结范围

“美术风格不改变”不是主观要求，而是下列可检测的不变量：

| 层级 | 必须冻结的内容 | 允许变化 |
|---|---|---|
| 全局语言 | PALIS 冷暗背景、Win95 窗口、档案纸张、印刷登记色、像素化边框与硬阴影 | 为可读性修复极小尺寸或溢出，但需截图批准 |
| 字体 | `Noto Serif SC Variable`、`Noto Sans SC Variable`、`IBM Plex Mono` 及现有后备字体顺序 | 不允许换成另一套字体系统 |
| 主色变量 | `--space`、`--cold-blue`、`--cold-red`、`--win-*`、`--paper*`、`--archive-*`、`--clerk-*` | 只能复用，不得在新组件另起一套主题 |
| 纹理与光标 | 现有纸张、网格、噪点、扫描线、登记色，以及 `/assets/cursors/retro-*.svg` | 可做压缩，不得改变肉眼观感与热点位置 |
| 窗口 | 标题栏、菜单、控制键、边框、阴影、任务栏按钮、焦点灰化、层级关系 | 内部状态和管理器可重写 |
| 动效 | 从触发点展开、内容延迟到达、最小化飞向任务栏、从任务栏还原、关闭收束 | `prefers-reduced-motion` 下允许按现有规则关闭 |
| 弹窗 | 提交确认、离开确认、冲突提示、审核决定、正式录入、删除/封存确认 | 文案和业务字段可增加，外观与开合行为不换皮 |
| 九类索引 | 第 18 节列出的九种排版、转场、节点/关系线/轨道运动 | 为扩展数量加入分页、聚合、避让和虚拟化 |
| 移动端 | 现有断点、任务栏、安全区、移动端禁拖拽行为 | 修复遮挡、滚动和触控可达性 |

当前基线变量以 `src/style.css` 为准。实施期间不能先删除旧变量或旧 class 再“凭感觉还原”；必须在新旧实现并存时完成逐像素和逐动作对账。

### 19.2 已核实的窗口现状

当前代码不是一套窗口系统，而是四套相近但不完全相同的实现：

| 表面 | 现有入口 | 当前能力 | 已发现差异 |
|---|---|---|---|
| 公开档案窗口 | `src/main.js` 的档案窗口管理段 | 焦点、层级、拖拽、任务栏、开合、最小化、还原、关闭 | 作为主要行为基线 |
| 助手/文档窗口 | `src/main.js` 的文档窗口管理段 | 与公开档案近似，但维护独立状态和任务栏 | 重复实现，后续容易漂移 |
| 书记官/管理员工作台窗口 | `src/archive-workflow/workspace.js` 的 `createWindow` | 焦点、拖拽、任务按钮、关闭 | 最小化使用 `hidden` 直接消失，没有主窗口的飞行动效和关闭状态保护 |
| 局部窗口 | `src/main.js` 的 local window system | 焦点、最小化、关闭、还原、最大化 | 计时和 class 名又是另一套 |

如果直接在工作台上继续堆业务按钮，弹窗和窗口行为会继续分叉。因此需要统一“窗口壳”，但不能在统一时改变外观。

### 19.3 窗口生命周期合同

共享窗口壳必须实现并记录以下状态机：

```text
closed
  → opening
  → active ⇄ inactive
  → minimizing → minimized
  → restoring → active
  → closing → removed
```

状态规则：

1. `opening` 期间只创建一个任务栏按钮；重复点击同一入口聚焦原窗口，不创建副本。
2. `active` 窗口取得最高层级；其他窗口标题栏进入现有非活动灰色。
3. 桌面端允许从标题栏和现有拖拽边缘移动，必须保留至少 28px 横向和 64px 纵向可抓取区域，不能拖到任务栏之后。
4. 宽度小于等于 760px 时保持现有“禁止拖拽”的行为。
5. 最小化后窗口不可点击，任务栏按钮仍存在；点击任务栏按钮触发还原而不是新建。
6. 关闭未保存的编辑器先进入 PALIS 离开确认窗；取消后原窗口、焦点和草稿均不变化。
7. 关闭结束才移除 DOM 和任务按钮，并把焦点返还给原触发按钮或下一个可见窗口。
8. `prefers-reduced-motion: reduce` 时跳过位移动画，但状态、焦点、任务栏和最终结果必须一致。
9. 动画中重复点击最小化、还原、关闭必须被幂等保护，不能产生孤儿任务按钮或已移除节点异常。

现有主要动画基线：

| 动作 | 时间 | 缓动 |
|---|---:|---|
| 窗口展开 `window-unfold` | 480ms | `cubic-bezier(.16, 1, .3, 1)` |
| 内容到达 `dialog-content-arrive` | 270ms，延迟 250ms | `cubic-bezier(.16, 1, .3, 1)` |
| 最小化 `window-minimize` | 260ms | `cubic-bezier(.55, 0, 1, .45)` |
| 还原 `window-restore` | 300ms | `cubic-bezier(.16, 1, .3, 1)` |
| 关闭收束 `window-task-close` | 240ms | `cubic-bezier(.55, 0, 1, .45)` |

除非验收截图和录像证明旧实现本身存在缺陷并得到委托人确认，否则不得调整这些数值。

### 19.4 共享 PALIS 窗口壳

计划新增的公共层：

```text
src/ui/palis-window-manager.js
  └─ 状态、唯一实例、z-index、焦点、任务栏、拖拽、最小化、还原、关闭

src/ui/palis-window-shell.js
  └─ 标题栏、菜单区、控制键、内容槽、确认窗接线

src/ui/palis-window.css
  └─ 从现有 CSS 原样迁出的公共窗口样式与动画
```

迁移顺序必须是：

1. 用真实浏览器冻结现有公开档案窗口和文档窗口的截图、状态和时间线。
2. 抽取公共层，但先只让公开档案窗口接入；数据与九类渲染不动。
3. 对账通过后接入文档窗口。
4. 再接入局部窗口。
5. 最后接入书记官/管理员工作台窗口，使其补齐同款开合、最小化、还原和关闭行为。
6. 四个表面全部通过后才能删除重复管理代码。

共享层只管理窗口，不知道档案类别、审核状态或数据库；业务页面作为内容插入。这样窗口重构失败时不会破坏档案数据，档案重构失败时也不会改变窗口。

### 19.5 九类动效冻结

除静态截图外，九类还必须分别保存动作基线：

- 科考站：路线展开、标注定位、缩放和选中反馈。
- 白幕入口：节点连线、聚焦、状态切换和坐标网响应。
- 生态：地层带切换、深度位置和内容展开。
- 人物：关系线揭示、节点进入、选中和退场。
- 事件：胶片图像、时间标记、选中与轨道移动。
- 国家、组织、异常、物种：现有卡片/通道/诊断/螺旋的进入、选中、翻页和退场。

每类在 0 条、1 条、当前基线条数和溢出条数四种数据量下验证。允许布局位置随数据改变，不允许删除该类独有的视觉语法。

### 19.6 视觉功能开关与回退

建议的独立开关：

```text
archive_window_shell_v2
archive_editor_v3
archive_index_v2_country
archive_index_v2_organization
archive_index_v2_station
archive_index_v2_entrance
archive_index_v2_ecology
archive_index_v2_person
archive_index_v2_event
archive_index_v2_anomaly
archive_index_v2_species
```

每个九类开关只决定该类别从旧目录还是新投影读取；窗口壳开关只决定窗口生命周期实现。上线期间旧渲染器保持只读可回退，不能让一个总开关同时切换全部九类。

### 19.7 明确禁止

1. 不引入 React、Vue、Tailwind 或通用后台 UI 套件来替代现有 PALIS。
2. 不把全部 `innerHTML`、窗口管理、数据库调用和九类布局在同一次改动中重写。
3. 不在视觉基线建立前重命名或删除现有 CSS 变量、动画和关键 class。
4. 不只靠源码正则测试判断视觉通过；必须使用真实浏览器、截图和动作测试。
5. 不因“新架构更整洁”而移动按钮、改变弹窗尺寸、改文案层级或消除现有纹理。

## 20. 无登录本地管理员验证方案

### 20.1 目标

实施与验收不能依赖委托人先登录线上 Supabase。开发机启动后自动获得唯一的本地身份：

```text
身份：本地管理员
ID：local-admin
角色：admin
权限：九类新建、修改、扩展、提交、审核、录入、设定、正式档案管理、
      本地用户管理、附件、索引重建、封存、离线和恢复
```

该身份没有密码，不通过网络认证，只存在于本地验证模式。默认以管理员全权限工作；“权限预演”可临时按书记官或观察员视角计算按钮可见性和拒绝结果，但不创建第二个账号。

### 20.2 本地数据适配层

现有 `createArchiveWorkflowClient(supabase)` 直接依赖 Supabase。需要先抽出同一套业务接口：

```text
ArchiveWorkflowRepository
  ├─ SupabaseArchiveWorkflowRepository  生产环境
  └─ LocalArchiveWorkflowRepository     本地验证
```

本地实现使用独立 IndexedDB 数据库，不使用正式 `localStorage` 草稿键，也不发起 Supabase、Storage 或 Edge Function 请求。一个 IndexedDB `readwrite` 事务模拟正式录入的原子性：编号、版本、索引、审计、通知和引用要么一起成功，要么一起回滚。

本地夹具至少包含：

- 九类各一份正式档案。
- 一份现有科考站和一份现有白幕入口，供“只可修改”流程验证。
- 26、27、100、500 条事件数据集，供时间索引扩展验证。
- 退回件、冲突草稿、受限档案、封存档案、离线档案。
- 长标题、空可选项、超长词条、失效引用和附件上限样本。

### 20.3 本地验证按钮

| ID | 按钮/标识 | 逻辑 |
|---|---|---|
| DEV-01 | `LOCAL ADMIN / 本地管理员` | 固定显示在工作台状态区，明确当前数据不在线上 |
| DEV-02 | 重置验收数据 | 二次确认后仅重建 PALIS 本地 IndexedDB；不触碰其他站点数据 |
| DEV-03 | 导出验收数据 | 下载本地 JSON 快照，包含档案、版本、索引、流程和审计，不包含线上密钥 |
| DEV-04 | 导入验收数据 | 校验 schema 版本与校验和后，在单事务中替换本地验证库；失败保持原库 |
| DEV-05 | 权限预演 | 在管理员/书记官/观察员界面权限之间切换；退出预演立即恢复本地管理员 |
| DEV-06 | 注入失败 | 只在本地验证面板中模拟保存失败、发布第 N 步失败、断网和版本冲突 |
| DEV-07 | 清除本地附件 | 显示数量和体积，二次确认后只清除本地测试附件 |

“重置”“导入”“清除附件”属于破坏本地测试数据的按钮，必须使用现有 PALIS 确认弹窗，并明确显示目标数据库名和可恢复方式。

### 20.4 生产隔离

本地管理员需同时满足三重条件才可启用：

1. `import.meta.env.DEV === true`，生产构建时相关动态导入被移除。
2. 页面来源为 `localhost`、`127.0.0.1` 或 `[::1]`。
3. 启动脚本显式设置本地验证标记。

另外设置构建门禁：

- `npm run dev:local-admin`：启动本地管理员与本地数据。
- `npm run verify:local`：自动启动本地站点，执行真实浏览器完整流程后退出。
- `npm run build`：若检测到本地管理员标记、测试夹具入口或本地数据导入被打进 `dist`，直接失败。
- 生产代码不包含 service role key；本地模式也不需要任何 Supabase key。
- Cloudflare 预览和生产域名即使手工添加查询参数，也无法启用本地管理员。

### 20.5 本地与线上一致性边界

本地验证用于提前发现界面、状态机、索引、布局和事务编排错误，但不能替代 RLS 与真实 PostgreSQL 验收。因此采用两层门禁：

1. 日常开发门禁：本地管理员完整流程、浏览器截图、单元测试、构建全部通过。
2. 上线前门禁：在独立 Supabase 测试项目验证 RLS、数据库函数、并发取号和发布事务；得到委托人允许后才部署生产。

本地和线上仓库实现必须运行同一组合同测试。若同一输入产生不同状态、编号、索引或错误码，视为实现失败，不允许上线。
