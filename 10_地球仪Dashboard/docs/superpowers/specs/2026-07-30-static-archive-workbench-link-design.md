# 旧档案与书记官工作台联动设计

## 目标

让所有已公开的原始档案与后来由书记官创建的档案使用同一套创建、修改、审核、发布和版本记录流程，同时保持原公开页面的既有视觉与排版。

## 范围

- 将每一份现有静态档案导入为服务器中的公开档案记录及其首个原始版本。
- 从原始档案页发起“提交本记录的修改申请”时，工作台读取该首个版本，自动填入对应表单、正文、自定义段落与已有媒体。
- 书记官在任一分类中新建档案时，按现有“新建档案—提交审核—发布”的流程生成独立记录；同一国家、组织或其他目录对象可以拥有多份档案。
- 审核通过的新增和修订档案均进入现有公开目录和版本历史；修订不会覆写原始版本。
- 继续使用现有分类模板、图片插槽和书记官权限。公开页面不增加“官方档案”横幅或替换为新的版式。

## 数据模型与流程

每份档案对应一个 `archives` 记录和一个初始的 `archive_versions` 版本。静态档案的服务器记录标记为原始来源，仅用于建立可编辑的底稿；它与书记官后续发布的新建记录一样可被目录、工作台和审核队列识别。

“修改申请”创建 `kind = amendment` 的草稿，来源为该档案当前公开版本。编辑器读取底稿后预填，提交和审核仍使用已有的贡献、审核、发布 RPC。审核发布生成新版本，不改写旧版本。

“新增档案”仍创建 `kind = new` 的草稿。发布后获得独立的服务器档案 ID、编号、版本和公开目录条目；它不会与同目录中已有档案共享或覆盖正文。

## 导入策略

导入通过可重复执行的 Supabase 迁移完成。每个分类从现有 `ARCHIVE_ROOTS` 和对应原始页面内容转换出与工作台一致的编辑文档；迁移以档案编码为幂等键，只补齐缺失的服务器记录、原始贡献与版本，绝不改写已存在的书记官版本或用户内容。

图片保留现有静态资源 URL；后续书记官新增或替换图片继续走现有附件上传流程。原静态资源不会被复制、删除或重命名。

## 错误处理

若某个公开静态档案尚未完成导入，修改入口显示明确的“档案底稿尚未同步”提示而不是打开空表单。导入完成后，同一入口自动恢复为预填编辑。

## 验证

- 自动化测试覆盖：静态档案有服务器 ID 时修改入口请求原始版本；没有 ID 时不允许空白修改；新建档案仍创建独立记录。
- Supabase 迁移测试覆盖全部现有分类的幂等导入、原始版本存在、不会覆盖既有版本。
- 浏览器测试覆盖一份旧档案的预填修改、审核发布、版本历史，以及同分类下新建第二份档案。
- 构建并执行与本次改动相关的测试；当前工作区已有的无关失败将单独列出，不以它们掩盖本次验证结果。
